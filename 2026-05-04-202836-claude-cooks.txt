● Good catch — let me update both points.

  Supabase keys

  You're right, I was using legacy terminology. New format:
  - sb_publishable_... — frontend (already in your .env). ✓
  - sb_secret_... — backend (Railway + Modal). Replaces service_role. Generate
  from Settings → API Keys → Secret keys → "Create new secret key" (name it
  something like foundry-backend).

  Important consequence for the plan: Supabase pairs the new key system with
  asymmetric JWTs (RS256, verified via JWKS). The old SUPABASE_JWT_SECRET HS256
  approach in api/plan.md is the legacy path. Two options:

  ┌────────────┬────────────────────────────────────────────────────────────┐
  │  Approach  │                            How                             │
  ├────────────┼────────────────────────────────────────────────────────────┤
  │ Asymmetric │ Railway fetches https://zaafausyullnzgbacnlw.supabase.co/a │
  │  (recommen │ uth/v1/.well-known/jwks.json once, caches the public keys, │
  │ ded, futur │  verifies user JWTs with RS256. python-jose supports this  │
  │ e-proof)   │ directly. No shared secret env var.                        │
  ├────────────┼────────────────────────────────────────────────────────────┤
  │ Legacy     │ Settings → JWT Keys → keep "Legacy JWT Secret" enabled;    │
  │ HS256      │ use the SUPABASE_JWT_SECRET env var as originally planned. │
  │            │  Works today, will eventually be deprecated.               │
  └────────────┴────────────────────────────────────────────────────────────┘

  I'll go with asymmetric/JWKS. Cleaner, no secret to leak. I'll update
  final_plan.md to reflect this.

● 2. Railway Redis env var — yes, you need to wire it

  When Railway adds a Redis service (private) to a project, it does not
  automatically inject REDIS_URL into your other services. You have to reference
   it explicitly via Railway's variable-reference syntax. Each service in a
  Railway project has its own isolated env scope.

  In your foundry API service:

  1. Service → Variables tab → New Variable
  2. Name: REDIS_URL
  3. Click the small </> "Reference" toggle (or just type the template):
  ${{ Redis.REDIS_URL }}
  3. (Replace Redis with whatever you named the Redis service if different —
  autocompletes when you type ${{.)
  4. Save → service redeploys → REDIS_URL is now in os.environ.

  Variables Railway creates on the Redis service include REDIS_URL,
  REDIS_PRIVATE_URL, REDIS_PUBLIC_URL, REDISHOST, REDISPORT, REDISPASSWORD. Use
  REDIS_PRIVATE_URL if Railway warns about egress costs — it's the
  internal-network URL (no egress fees, lower latency). For dev / single-region
  projects either works.

  Same pattern for any other vars you want to share between services.

  While you're at it, double-check the foundry API service Variables tab also
  has:
  - SUPABASE_URL
  - SUPABASE_KEY (the sb_secret_... value)
  - MODAL_TOKEN_ID and MODAL_TOKEN_SECRET (for run_job.spawn(...) from Railway →
   Modal)

  Push the modal_worker.py change and the next Railway build should boot past
  lifespan.

● modal deploy is the command — modal run was just for the one-shot weight
  upload.

  source .venv/bin/activate
  modal deploy api/modal_worker.py

  What this does:
  1. Builds the image on Modal's side (apt install git, pip install
  rc-foundry[rfd3,sae,api] + supabase + redis). First build takes 5–10 minutes —
   it pulls torch, atomworks, pymol, etc. Subsequent deploys are fast (cached
  layers).
  2. Registers the app as foundry with the function run_job callable from
  anywhere using your Modal token.
  3. Returns a URL like https://modal.com/apps/michaelwaves/main/ap-... — that's
   the deployed app's dashboard.

  After deploy, Railway's runner.py does from modal_worker import run_job; 
  run_job.spawn(...) and it works because:
  - Railway has MODAL_TOKEN_ID + MODAL_TOKEN_SECRET env vars (you added these).
  - modal[api] is installed in the Railway venv (it's in nixpacks.toml).
  - .spawn() sends an RPC to Modal which routes to the deployed run_job.

  Two things that will likely bite you on first deploy:

  1. Private GitHub repo: the image build does pip install 
  rc-foundry[rfd3,sae,api] @ git+https://github.com/michaelwaves/foundry@modal.
  If michaelwaves/foundry is private, the pip install will fail to clone. Either
   make it public temporarily, or add a GitHub PAT to the Modal secret and point
   the install URL to use the token. Easiest fix: add a token to the install URL
   via a Modal secret
  (https://${GITHUB_TOKEN}@github.com/michaelwaves/foundry@modal) — but that
  requires templating. Simpler is just push the modal branch to a public repo
  for now.
  2. foundry-secrets Modal secret: must exist with SUPABASE_URL, SUPABASE_KEY,
  REDIS_URL. You ran modal secret create earlier — verify with modal secret 
  list. Note: redis://default:...@redis.railway.internal:6379 only resolves
  inside Railway's private network — Modal containers can't reach
  redis.railway.internal. You need to use Railway's public Redis URL, which is
  exposed via the REDIS_PUBLIC_URL variable on the Redis service (or the
  dashboard's "Public Network" toggle). Otherwise the Modal worker will fail to
  connect to Redis.

  Iteration loop after the first successful deploy:
  modal deploy api/modal_worker.py     # production push (or use modal serve for
   live-reload during dev)

  Verify it's deployed:
  modal app list
  modal app logs foundry --tail        # watch live logs from spawned jobs

● Three schemes Redis clients accept:

  ┌───────────┬──────────────────────────────────────────────────────────────┐
  │  Scheme   │                             Use                              │
  ├───────────┼──────────────────────────────────────────────────────────────┤
  │ redis://  │ plaintext TCP — fine on private/trusted networks (e.g.,      │
  │           │ Railway internal).                                           │
  ├───────────┼──────────────────────────────────────────────────────────────┤
  │ rediss:// │ TLS-wrapped TCP — same protocol, encrypted. Use when         │
  │           │ crossing the public internet.                                │
  ├───────────┼──────────────────────────────────────────────────────────────┤
  │ unix://   │ local Unix socket — not relevant here.                       │
  └───────────┴──────────────────────────────────────────────────────────────┘

  Your error: you pasted redis-production-f745.up.railway.app — that's just the
  hostname, not a URL. The Python redis client needs the full form.

  Railway exposes both for the same Redis service in the Redis service's
  Variables tab:

  - REDIS_URL (private) → redis://default:WbyR...@redis.railway.internal:6379 —
  only resolves inside Railway's private network. Used by the Railway-hosted
  FastAPI.
  - REDIS_PUBLIC_URL (public) →
  redis://default:WbyR...@redis-production-f745.up.railway.app:<port> — public
  TCP proxy. The port is not 6379 — Railway assigns a random high port (look for
   RAILWAY_TCP_PROXY_PORT on the Redis service, often something like 12345).

  So for the Modal secret (Modal can't reach redis.railway.internal), you want
  REDIS_PUBLIC_URL. Update with:

  modal secret create foundry-secrets \
    SUPABASE_URL=https://zaafausyullnzgbacnlw.supabase.co \
    SUPABASE_KEY=sb_secret_REDACTED \
    REDIS_URL='redis://default:REDACTED@redis-production
  -f745.up.railway.app:<PORT>' \
    --force

  (--force overwrites the existing secret.)

  For the Railway service (your FastAPI), keep REDIS_URL=${{Redis.REDIS_URL}} —
  that's the internal one, faster and free egress.

  About TLS — Railway's public Redis proxy is plain TCP by default (redis://,
  not rediss://). Password auth still happens, but the wire is unencrypted. For
  a side project / hackathon this is fine. For production-grade, you'd front it
  with stunnel or use a managed Redis with TLS (Upstash, etc).

  hotspots: E64:CD2+CZ; E88:CG+CZ

  length:   100-150 (default)
  motif:    (none)

  The combo fails because:
  - No motif PDB → there's no chain E to attach hotspots to, no fixed atoms.
  - No contig → RFD3 doesn't know the design layout (which residues are designed
   vs preserved).
  - Hotspots-only isn't a valid design spec — hotspots refer to residues on a 
  target the binder should contact, so the target has to exist.

  motif:   tutorials/rfd3_ppi_tutorial/4zxb_cropped.pdb

  For pure de novo (no target), use only:

  length: 100-150
